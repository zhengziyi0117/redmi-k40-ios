# K40 native apps and persistent data

This work tests native ARM64 iOS applications on the existing iOS 16.5 port. It does not provide Apple ID activation, App Store purchases, FairPlay decryption, or Android APK compatibility.

手机上用 **TrollStore** 安装已有的未加密 ARM64 iOS IPA，可从它的“＋”菜单尝试文件或 URL 安装。小型原生 Ibili 已由其官方 helper 安装并注册；安装器自身界面也已实机打开。当前可保存的数据上限为 **240 MiB**，已有应用和照片等会占用其中一部分；这不是 Android 剩余空间的共享挂载。照片已显示并在重启后保留真实导入的测试图。**B 站修改版仍有导航缺字和视频显示问题，不能当作已适配完成。**

## Storage layout

Android's F2FS userdata is encrypted. Its free space cannot be mounted directly by this XNU port. No GPT or userdata resizing is performed.

This phone's 1 GiB `cust` partition contains an ext4 filesystem only 3,743,744 bytes long. The full original partition, including stale data after that filesystem, is backed up as `backups/20261106/before-app-data/cust.img`, SHA-256 `b5d07b1f202635a07c891777aca1f50ed00e443846aea55ba69b065c9e5f7ce1`.

| Range in cust | Purpose |
| --- | --- |
| 0–8 MiB | Original bytes preserved, including the entire ext4 filesystem |
| 8 MiB | Versioned 64-byte `K40DATA1` descriptor with CRC-32 |
| 16–512 MiB | Read-only compressed APFS application image |
| 512–1024 MiB | Two alternating 256 MiB data archive slots |

Only the final region is writable from iOS. The loader exposes it as a bounded virtual partition, `iosdata`, and applies the parent-relative offset to every read, write and verification read. Both loader and kernel validate its exact geometry. The original `cust` device, application image, Android userdata and GPT remain read-only from iOS.

APFS in this port is read-only. Data uses the existing RAM filesystem and archive checkpoint mechanism, extended to include photographs, app containers, documents and launcher settings. This is not a general writable APFS implementation. Saving is periodic and requested on orderly shutdown. A forced power loss can lose changes since the last completed checkpoint; simultaneous app database writes are a remaining consistency limitation. A real, enforced 240 MiB file-byte limit leaves space for metadata in a 256 MiB archive slot. Native statfs reports 251,658,240 bytes total. Sparse growth is included, while 16 KiB RAM page rounding is not charged for every small file. Test 16 rejected oversized sparse growth with ENOSPC and created/removed 1000 tiny files successfully. Physical RAM has its own independent limit. The second archive slot is a recovery copy, not additional user capacity. Temporary installers, system indexes/logs and app Library/Caches have separate volatile RAM mounts; they do not increase persistent capacity. Selected preferences/history from mobile/Library are still checkpointed. Large video downloads and large new IPA bundles are unsuitable for this allocation.

## Application placement

Original system apps and the Bilibili test bundle are copied into a separate RAM filesystem at `/Applications` before launchd starts. Bundles contain real files: LaunchServices rejects symlink-only app bundles. The compressed immutable source remains in `iosapps`. The original system image and installed v1.4 boot remain available for rollback during testing.

The Bilibili test is **BiliBiliMApp 8.89.0 / mod 3.1.0**, a modified client from [TouchFriend's release](https://github.com/TouchFriend/BiliBiliMApp/releases/tag/3.1.0), not an unmodified App Store download. The native feed and thumbnails load. The user reported missing-glyph boxes and black, silent video. CoreText subsequently verified PingFang SC glyph coverage and fallback; AVAssetReader returned 24 H.264 image buffers from a generated local test clip. Buffer delivery alone does not verify decoded pixels or Bilibili playback. The pinned bundle contains four placeholder text fonts with only four glyphs each. The UUID-guarded adapter registers bundled fonts, maps those specific font names to PingFang, and requests software decoding through IJK options. Ordinary Chinese feed titles display, but navigation glyphs remain missing. Test 19 reported ongoing video-frame decode notifications, first audio/video rendered notifications and system audio playback, while its screenshot still showed a black video rectangle. Audible output is not yet confirmed.

Tests 21–23 identified the active `IJKVideoRenderer -display_pixels:` path and its private `IJKOverlay`, rather than the older public `IJKSDLGLView` or public AVSampleBufferDisplayLayer enqueue API. Its `_VTB` overlay holds a CVPixelBufferRef at +48; this is guarded by the pinned executable UUID and the exact load instruction in its own converter. The CPU presenter received 1080p NV12 buffers and displayed a green, incorrect image. Sampled buffers included both plausible luma/chroma ranges and near-zero chroma; requesting `videotoolbox=0` immediately before prepare did not resolve this. Neither decoded notifications nor a successful pixel-buffer lock is evidence of correct playback. These CPU presentation paths remain opt-in and are omitted from the default stored boot arguments. Release builds do not redirect all Bilibili stderr or enable its notification tracing; `run_wifi_probe.py` explicitly enables local diagnostics.

The checked pre-v1.5 backup identified about 138 MiB in Bilibili's `Library/Application Support/modmgr`. These are downloadable code/resource modules, not user documents. The root setup job verifies `MCMMetadataIdentifier=tv.danmaku.bilianime`, copies this directory to the separate temporary mount before removing the original, mounts a bounded RAM filesystem, and copies the files back. Copy failure retains the source or temporary copy; mount failure restores ordinary contents. A root-owned, validated path marker tells the saver to omit this cache. Test 20 migrated it successfully and reduced the archive from about 203 MiB to 70 MiB (generation 174, 73,510,152 bytes). Later boots rebuild these modules from the network. App documents/preferences and the real Photos library remain selected for persistence. The full original live cust and boot_b were saved and SHA-256 checked under `backups/20261107/pre-v1.5` before migration.

The on-phone installer is [TrollStore 2.1.1](https://github.com/opa334/TrollStore/releases/tag/2.1.1). Its bootstrap helper stays outside `/Applications`: otherwise the official helper classifies TrollStore itself as an immutable system app and refuses installation with code 179. Device tests completed bootstrap, ldid installation, HTTPS download with pinned SHA-256, signing and installation of the small native Ibili IPA (helper exit 0). Installed bundles survive subsequent archive restores. Native launch of TrollStore was accepted on test 13, and test 16 captured its real Apps list with Ibili. Test 17 also accepted native launch of `app.ibili.client`; playback in this alternative has not been tested.

Two compatibility layers are explicit. The exact TrollStore helper UUID and instruction bytes are checked before adapting its unavailable AMFI developer-mode query; this kernel already permits development code. FrontBoard also independently refused container-installed apps with security error 3. The separate GPL-3.0-or-later application-trust library adapts [AppSync Unified's public FrontBoard hook](https://github.com/akemin-dayo/AppSync/blob/235aca6cddfbdc9fa87fcb5b2aec2df37ed6d65a/AppSyncUnified-FrontBoard/AppSyncUnified-FrontBoard.x). It accepts only locally marked TrollStore bundle paths. Because SpringBoard cannot traverse every private container, the root helper publishes a root-owned readable path list atomically after exit. `/var` and `/private/var` paths are normalized before comparison. Other applications retain the original decision. Apple ID and FairPlay are not implemented by these changes.

## Photos and Files

The previous root omitted `com.apple.assetsd` and `com.apple.FileProvider`. Files repeatedly failed to resolve the latter and exited with SIGTRAP. The test root now includes these jobs, `com.apple.mobile.installd`, and the stock CoreSpotlight/search services. Font services, MediaParser and the keyboard service are also included. Files' Recents page now displays its normal empty state instead of crashing or reporting unavailable content. Full local Browse/file-picker operation is not yet verified.

The PhotoKit probe, running as mobile, imported `K40-storage-test.png` through the real `PHPhotoLibrary` API: success, no error, asset count 0 → 1. This is a generated test image, not an Android personal photo. The next boot restored the checked archive (generation 4, 14,102,400 bytes) and queried one asset without reimporting. The real Photos UI subsequently displayed the saved gradient image. Evidence: `runtime/validation/20261106/apps-data03/live03/screen.png`. Release roots omit the automatic sample importer.

## Reproduction and safeguards

The installed v1.5/code6 storage boot restored generation 226, reached the desktop, autojoined Wi-Fi, and returned HTTP/HTTPS 200. An orderly stop returned to Android A (bootctl slot 0, boot complete 1), and the installed module's read-only check passed. All three storage images read back as built; only boot_b needed an update. The final data snapshot has CRC-valid generations 230/231, 80,331,392 bytes each, both installed native app IDs and one real Photos asset. Evidence is under `runtime/validation/20261107/apps-stored`; the current phone is left in Android for charging. Rollback inputs and the final data snapshot are under `backups/20261107/apps-v1.5`.

Build with `scripts/build_loader.sh`, `scripts/build_wifi_kernel.sh` and `scripts/build_app_data.sh`; prepare the root with `scripts/prepare_wifi_root.py --app-data` alongside the validated display/audio/Bluetooth flags. `--open-app BUNDLE_ID` is a diagnostic launch, not a release feature.

`prepare_app_data.py` creates a host image from the verified backup and hashed downloaded apps. `install_app_data.py` defaults to a read-only check. Its `--write` path refuses any cust whose checksum already differs from the original backup, preventing accidental replacement of a live data store. The first provision passed a complete 1 GiB loader read-back, CRC-32 `01b4fa7d`. `check_app_data_guard.py` compiles the actual loader discovery function and checks acceptance plus eight rejection cases, including filesystem overlap and corrupt descriptors.

Never reflash `cust-app-data.img` after use without first preserving its data slots. The normal iOS boot installer must not rebuild or replace this partition. To abandon this experiment, boot the prior v1.4 image; restoring the original cust backup removes all data created in this new archive.
